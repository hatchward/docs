Hosted agent-fleet runner

Enroll your machine. It runs what the control plane hands it.

Install the CLI, enroll with a one-time code, and the machine starts asking the hosted control plane for work. Each assignment spawns a coding-agent worker in its own container, on your machine, calling your own model accounts — no board credentials on the CLI, no local database to run, nothing to elect.

Structure

The runner enrolls and executes. Assignment lives with the control plane.

The binary you install is thin on purpose: identity, service supervision, and a container per assignment. What to run, in what order, and on which model is decided by the hosted control plane and arrives with the assignment itself.

Layer 1

the hatchward binary

Bare hatchward is the whole operator loop: it enrolls an unenrolled machine, then asks the hosted control plane for work and spawns and watches a containerized worker for each assignment it gets.

It owns runner identity, container isolation, and boot-time supervision — nothing else runs locally.

Layer 2

the hosted control plane

Your board, your routing, and which model and role each task calls for are configuration on the hosted side. The assignment a runner receives already carries the normalized fields a worker needs.

Worker-facing board, ask, and lifecycle operations route through assignment-scoped hosted APIs — the CLI itself holds no board credentials.

Projects

One runner, as many projects as you enable.

A machine enrolls once. Which hosted projects it actually works, and where each project's workspace lives on disk, is a separate, per-machine choice.

  • List project list Every project this machine has enabled, per its own runner.yml.
  • Enable project enable <id> With --workspace-root <alias> --path <dir>, binds a hosted project to a local directory under an alias you name.
  • Disable project disable <id> Stops this machine picking up work for that project; the workspace alias is left in place.

No board credentials on the CLI. Board, routing, and worker-facing lifecycle operations run through hosted APIs scoped to the assignment — the runner never holds a token that could reach your board directly.

Where it runs

Nothing dials in.

Every connection the runner makes is one it opened. It calls out to the hosted control plane for assignments, and the container it spawns for each one calls out to your own model vendor account for inference. Nothing reaches back in.

Cost shape

your accounts, your rates

Model spend runs on the accounts you already hold. No per-seat, no per-task markup, no metered middleman standing between you and the model.

Capacity

the machine you buy

No shared tenancy, no queue behind somebody else's customers, and no rate limit you did not set yourself.

Procurement

no new vendor on the network

Whatever your build machines already reach, the agents reach: same VPN, same egress rules, same secrets manager, same git credentials. Nothing new to approve.

Workers are sandboxed. Every assignment runs in its own container, spawned and watched by the runner — isolation is not a setting you choose, it is the only mode there is.

One thing this does not claim: your code does leave the network, on the model call you were already making. What is added is the runner's own outbound connection to the hosted control plane that hands out assignments.

Coordination

Assignment lives in one place, not brokered by each machine.

Every runner asks the same hosted control plane for work; nothing is negotiated between machines. There is no leader to elect and no registry to poll, because there is only one authority.

What the control plane owns

assignment, routing, the audit trail

A task goes to exactly one runner, at a time the control plane decides. Board state, routing rules, and the record of what ran, where, and why are all hosted — not something any one machine's crash or restart puts at risk.

What the runner owns

its own identity, and nothing else's

A runner knows who it is and which projects it has enabled. It asks for work, executes what it is given in a container, and reports back — it holds no opinion about any other machine in the fleet.

What the runner guarantees

Small surface, so there is less to get wrong.

The cutover traded a scheduler's worth of local guarantees for a hosted control plane's. What is left on the machine is deliberately narrow.

  • Identity fails loud runner.identity A corrupt or unreadable identity file is returned as an error, never silently re-enrolled — a crash-recovery guard against re-registering a machine that already has a history.
  • One mode of isolation container Every assignment runs in its own container, spawned and watched by the runner. It is not a setting — there is nothing else to choose.
  • Restart, don't babysit hatchward service install A launchd or systemd unit supervises the process, so a crash or a reboot resumes on its own — no terminal or tmux session to keep alive.
  • Scripted enrollment --code-stdin Provisioning scripts and CI pipe the one-time code instead of typing it; a boot-service unit with no TTY fails fast with a named error rather than hanging on a prompt.

Not part of this cutover: hatchward doctor and hatchward config show/open are deferred to a follow-up. Today the runner either enrolls and runs, or tells you exactly why it couldn't.

Setup

Three commands. The first one asks for a code.

One line on macOS and Linux — curl -fsSL https://hatchward.dev/install.sh | sh — or brew install hatchward/tap/hatchward. Checksummed tarballs for the four targets every release builds. The runtime is POSIX-only; Windows is not supported in v1. 

# first run: asks for your enrollment code, then runs
$ hatchward

# enable a project, and where its workspace lives on disk
$ hatchward project enable acme-web \
    --workspace-root web --path ~/fleet/acme-web

# keep it running across reboots and crashes
$ hatchward service install

Bare hatchward is the whole loop. On a machine that has not enrolled yet, it prompts for a one-time enrollment code and enrolls before it runs; on a machine that already has, it starts asking the hosted control plane for work immediately. Scripted or unattended setups skip the prompt with hatchward enroll --code-stdin, piping the code on stdin.

Enabling a project binds a hosted project id to a local directory under an alias you choose, with project enable <id> --workspace-root <alias> --path <dir>. A machine can have more than one project enabled; project list shows what is, and project disable turns one off without discarding the alias.

service install registers the runner as a boot-time service — launchd on macOS, systemd on Linux — so it survives a reboot or a crash without anyone watching a terminal. service status and service uninstall round it out.

Verifying a download

A checksum, and platform-native signing.

SHA256SUMS in the release proves the tarball and the manifest agree with each other, not where either came from. Apple Developer ID codesigning and notarization, and Windows Authenticode, are supported in the release pipeline where the platform credentials are configured; Homebrew installs whatever the tap's formula points at.
