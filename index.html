Your board. Your repos. Agents on your machines.

Create an account, connect your board and repositories in the Hatchward console, and publish a project. Then enroll any machine you own with a one-time code. It runs each ticket in its own container, on your own model accounts, and your credentials never leave it.

How it works

Set up the project in the console first. Machines come after.

Everything about what to run lives in your Hatchward account: the board, the repositories, which agent takes which ticket. A runner joins later, with a code issued for the projects it should work, and asks for nothing else.

Step 1 · Account

sign up at the console

Enter your email at dash.hatchward.dev. A single-use code arrives by email, and the same screen signs you in or creates your account. There's no password to set or lose.

Pick a plan under Plan & billing. Enrolling runners needs an active plan.

Step 2 · Project

walk the setup wizard

Connect your board and GitHub under Integrations, then create a project. The wizard has five steps: Board, Repositories, Map tickets, Agents & routing and Review & publish.

Nothing takes effect until you publish it. Repository access goes through the GitHub App, so you never type a token into the console.

Step 3 · Runner

enroll your machine

In the console, choose the projects a machine should work and generate an enrollment code. Install the CLI on that machine, run hatchward enroll and paste the code.

Enrolling turns on every project the code was issued for. The runner then waits for assignments, and the console shows each one as it runs.

Secrets

Your credentials stay on your machine. The agent never holds one.

Hatchward's account knows which project needs which secret. It never sees the values. They live on the runner, and the runner adds each one to the agent's request on the way out, so the code the agent runs can't read or leak them.

On the host

values never reach Hatchward

Model keys and tokens are files in the runner's home, set per project, readable only by the runner's own user. They're read when an assignment starts and cleared from memory when it ends. They never travel to the control plane, and never appear in the runner's arguments, environment or config.

In the container

a placeholder, not a key

The agent's container has no network of its own. Its traffic goes through a proxy the runner starts for that one assignment. The proxy swaps a placeholder for the real credential on the request to the model or GitHub, so the real value never enters the container.

At the edge

an allowlist you control

The proxy refuses any host that isn't on the allowlist: the runner's own short base list, plus exact hostnames you add. It closes when the assignment ends, and its access token stops working at the same moment.

In development

Next for secrets. This is being designed now and isn't in a release yet; the details may change before it ships.

  • Declared secrets per project A project names the secrets its agents need and where each one may be sent. You supply the values on the runner and approve each destination there; a later change to the project can't redirect a secret or open new egress until you confirm it on the machine.
  • Brokers use, don't read A companion container, on an image you trust, holds a secret the agent can use but never see — an SSH agent for git, or an auth proxy in front of a database.
  • Short-lived GitHub tokens one repo, one assignment Each assignment gets a GitHub App token scoped to the one repository it works on, minted when needed and never stored, in place of a long-lived personal token.
  • Two keys per project console + runner A runner is offered a project only when your account has granted it and the machine's operator has enabled it and supplied its secrets. A stolen runner key can't reach a project the account never gave that runner.

Structure

The console decides what runs. Your machines run it.

The binary you install is thin on purpose: identity, service supervision, and a container per assignment. What to run, in what order, and on which model is set in the console and arrives with the assignment itself.

Hosted

the Hatchward console

Your board, your repositories, your routing, and which model and role each task calls for are set up here. So are your runners: you issue their enrollment codes, choose their projects, and watch their work live.

The assignment a runner receives already carries what its worker needs, so no board credential ever sits on a machine.

On your machines

the hatchward runner

hatchward enroll joins a machine to your account. After that, bare hatchward holds a connection to the control plane, receives assignments, and starts and watches a container for each one.

It owns the runner's identity, container isolation, your credentials, and restart on boot. Nothing else runs locally.

Where it runs

Nothing dials in.

Every connection the runner makes is one it opened. It calls out to the hosted control plane for assignments, and the container it spawns for each one calls out to your own model vendor account for inference. Nothing reaches back in.

Cost shape

your accounts, your rates

Model spend runs on the accounts you already hold. No per-task markup and no metered middleman between you and the model.

Capacity

the machine you buy

No shared tenancy, no queue behind somebody else's customers, and no rate limit you did not set yourself.

Procurement

no new vendor on the network

Whatever your build machines already reach, the agents reach: same VPN, same egress rules, same git credentials. Nothing new to approve.

One thing this does not claim: your code does leave the network, on the model call you were already making. What is added is the runner's own outbound connection to the hosted control plane that hands out assignments.

What the runner guarantees

Small surface, so there is less to get wrong.

Assignment, routing and the audit trail live in one place, the control plane. No machine negotiates with another, so there's no leader to elect and nothing to split. What's left on each machine is deliberately narrow.

  • Identity fails loud runner.identity A corrupt or unreadable identity file is returned as an error, never silently re-enrolled, so a machine that already has a history is never registered twice.
  • One mode of isolation container Every assignment runs in its own container, spawned and watched by the runner. It is not a setting — there is nothing else to choose.
  • Restart, don't babysit hatchward service install A launchd or systemd unit supervises the process, so a crash or a reboot resumes on its own. Homebrew's brew services works too.
  • Says why it's idle hatchward project list When a project can't run on a machine, the runner names the reason in its log and in the console, instead of quietly taking no work.
  • Scripted enrollment --code-stdin Provisioning scripts and CI pipe the one-time code instead of typing it; a boot service with no terminal fails fast with a named error rather than hanging on a prompt.

Enroll a runner

An account first. Then three commands.

Create an account and publish a project before you touch a machine: the enrollment code comes from the console. Then install with curl -fsSL https://hatchward.dev/install.sh | sh or brew install hatchward/tap/hatchward, on macOS or Linux. Docker must be installed and running. 

# install the CLI
$ curl -fsSL https://hatchward.dev/install.sh | sh

# enroll with the code from the console
$ hatchward enroll --name build01

# keep it running across reboots and crashes
$ hatchward service install

Get the code from the console. Open Fleet, choose the projects this machine should work, and generate an enrollment code. The console shows the commands to copy. A code works once, and only for a short time.

hatchward enroll asks for the code, then for a folder to keep the projects' workspaces in, and turns on every project the code was issued for. Scripts can pipe the code with --code-stdin. On a machine that's already enrolled, bare hatchward starts asking for work straight away.

service install registers the runner as a boot-time service — launchd on macOS, systemd on Linux — so it survives a reboot or a crash without anyone watching a terminal.

Credentials and image settings are covered in the install guide.
